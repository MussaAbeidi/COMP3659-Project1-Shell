### Division of Labour & Planning
<small>Last Updated: 09/13/2026</small>
> Work will be divided based on functionality milestones. Members will take ownership of a specific feature/module (e.g., basic execution, background jobs, pipelines) to ensure there are no merge conflicts. In order to prevent two members from working on the same feature accidentally we will communicate through Discord to let other group members know what feature we are working on and a timeline when it will most likely be completed. In the case of a group member working on a feature that requires a different feature that another group member is working on, fake data will be used to test the code in the meantime. Additionally, group members will draft high-level design documents prior to coding to ensure everything follows the requirements and progresses properly. Finally, there will be frequent meetings and check-ins to ensure everyone is on the same page.

## Development Methodology
<small>Last Updated: 09/13/2026</small>
### Always Syncing

> Before modifying any file, we will ensure that our local ```main``` is up to date with the remote repository so that we don't accidentally overwrite each other's work.

> Our GitHub repository serves as our primary project backup. By adhering to our group policies of frequently pushing local commits to GitHub, we ensure no local hardware failure will result in the loss of our project code or documentation and the project progress will proceed smoothly.

### Isolate Work

> We never commit to ```main``` directly. Instead, we will create a fresh branch for the specific task we are working on using a plain English naming scheme (Ex: ```add/background-jobs``` or ```patch/signal-handler```).

### Meaningful Commits

> We will always push work with commit messages that tell the rest of the group *why* the change was made, rather than a simple "updated code" or no commit message at all.

### Pull Requests

> Once a feature is fully tested and compiling on the Linux VM, we will push the branch and open a Pull Request on GitHub. This will be done with a clear and detailed title and description. Then, we require at least one other group member to review the code changes, test them, and either approve it or deny it (with a comment in reply elaborating on why it is denied). Once approved, then it will be merged to ```main```. Finally, after it has been merged, the branch will be deleted to keep the repository clean and organized.
